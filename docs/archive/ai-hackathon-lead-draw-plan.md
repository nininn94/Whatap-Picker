# 오프라인 부스 리드 모객을 위한 AI 뽑기 이벤트 시스템

> **사내 AI 해커톤 기획안 초안**

부스 방문자가 줄을 서는 동안 모바일 설문을 완료하고, 차례가 되면 이름과 휴대폰 뒷자리 확인만으로 경품 뽑기에 참여하는 시스템입니다. 설문 데이터, 추첨 결과, 일자별 경품 재고, 리드 품질 분석을 하나로 연결해 현장 운영 시간을 줄이고 후속 마케팅 효율을 높이는 것이 목표입니다. 해커톤에서는 Codex, Claude Code 등 AI 코딩 도구를 활용해 MVP를 빠르게 구현하는 방식으로 진행합니다.

| 항목 | 내용 |
| --- | --- |
| 논의 일정 | 화요일 개발자 미팅용 |
| 팀 구성 | 마케터 1명 · 프론트엔드 개발자 1명 · Java 개발자 1명 |
| 권장 MVP | 설문 · 검색 · 추첨 · 재고 차감 · AI 리드 분류 |

---

## 1. 문제 정의

현재 오프라인 부스에서는 설문 참여 후 실물 뽑기판으로 경품 이벤트를 운영하고 있습니다. 참여율은 높지만 설문 작성, 인적사항 확인, 뽑기, 경품 지급 과정이 순차적으로 진행되어 한 명당 처리 시간이 길어지는 문제가 있습니다.

- 설문 작성과 현장 확인이 같은 지점에서 이루어져 대기 시간이 증가합니다.
- 전화번호, 회사명, 이메일 등 리드 정보의 정확도를 현장에서 수동으로 확인해야 합니다.
- 등수별 경품 수량과 일자별 잔여 수량을 운영자가 직접 관리해야 합니다.
- 이벤트 결과와 설문 데이터가 분리되면 사후 분석과 영업 후속 조치가 늦어집니다.

> **핵심 개선 방향:** 설문은 대기 중 모바일에서 완료하고, 운영자는 최소 정보 확인 후 즉시 추첨과 지급 처리만 수행하도록 흐름을 분리합니다.

## 2. 해커톤 개발 방식

이번 프로젝트는 개발자가 처음부터 직접 구현하는 방식이 아니라, AI 코딩 도구를 활용해 요구사항 정의, 코드 생성, 오류 수정, 테스트 보완, 문서화를 빠르게 수행하는 것이 핵심입니다.

| 구분 | AI 활용 방식 | 팀에서 확인할 부분 |
| --- | --- | --- |
| 기획/요구사항 | Codex 또는 Claude Code에 기능 명세, 화면 흐름, 데이터 구조 초안을 작성하게 함 | 마케터가 현장 운영 정책과 예외 조건을 검수 |
| 프론트엔드 | 모바일 설문 화면, 운영자 검색 화면, 뽑기 결과 UI를 AI로 생성하고 수정 | 프론트 개발자가 UI 상태, 입력 검증, 사용성 확인 |
| 백엔드 | Spring Boot API, 데이터 모델, 일자별 참여 제한, 추첨 로직을 AI로 초안 구현 | Java 개발자가 재고 차감, 중복 참여 검증, 저장 로직 검토 |
| 테스트/디버깅 | AI에게 주요 시나리오 테스트 케이스와 오류 수정안을 생성하게 함 | 팀원이 실제 데모 흐름으로 동작 검증 |
| 발표 | AI로 개발 과정 요약, 아키텍처 설명, 데모 시나리오 초안 작성 | 문제 해결 효과와 현장 적용 가치를 중심으로 정리 |

> **발표 포인트:** "AI 기능이 들어간 서비스"뿐 아니라, 실제 MVP 개발 과정 자체를 AI 코딩 도구로 단축했다는 점을 함께 보여줍니다.

## 3. 서비스 개요

방문자는 QR코드로 설문에 참여하고, 운영자는 이름과 휴대폰 뒷자리로 해당 방문자를 조회합니다. 조회된 방문자가 설문을 완료했고 해당 행사 일자에 아직 뽑기에 참여하지 않았다면, 운영자 화면에서 추첨을 실행합니다. 시스템은 남은 경품 수량을 기준으로 등수를 결정하고 결과를 데이터에 저장합니다.

| 구분 | 내용 | 성과 지표 |
| --- | --- | --- |
| 현장 운영 | 설문과 뽑기 대기 흐름을 분리해 부스 회전율 개선 | 1인당 처리 시간, 대기열 길이 |
| 리드 데이터 | 입력값 검증, 일자별 참여 제한, 설문·추첨 결과 통합 저장 | 유효 연락처 비율, 일자별 참여 관리 정확도 |
| 마케팅 활용 | AI 리드 등급 분류와 후속 메시지 초안 생성 | 상담 희망 리드 수, A등급 리드 수 |

## 4. 사용자 흐름

### 방문자

1. 부스 앞 QR코드 스캔
2. 모바일 설문 페이지 접속
3. 이름, 연락처, 회사명, 관심 제품, 상담 희망 여부 입력
4. 개인정보 수집 동의와 마케팅 활용 동의 후 제출
5. 대기 후 차례가 되면 이름과 휴대폰 뒷자리 전달
6. 운영자 확인 후 뽑기 결과 확인

### 운영자

1. 운영자 화면에서 이름 + 휴대폰 뒷자리 검색
2. 설문 제출 여부와 해당 일자 참여 여부 확인
3. 뽑기 실행 버튼 클릭
4. 당첨 등수와 경품명 확인
5. 당첨 결과 확인 후 경품 지급
6. 결과 자동 저장 및 잔여 수량 차감

| 우선순위 | 기능 | 설명 | 담당 논의 |
| --- | --- | --- | --- |
| 필수 | 모바일 설문 | QR 접속, 리드 정보 입력, 개인정보 수집 동의, 마케팅 활용 동의, 제출 완료 화면 | 마케터 + 프론트 |
| 필수 | 참여자 검색 | 이름과 휴대폰 뒷자리로 설문 제출자를 검색 | 프론트 + 백엔드 |
| 필수 | 일자별 참여 제한 | 행사 기간이 여러 날이면 같은 사람도 하루 1회까지 참여 가능 | 백엔드 |
| 필수 | 수량 제한 추첨 | 행사 일자별 1~5등 잔여 수량을 기준으로 결과 생성 및 차감 | 백엔드 |

| AI | 리드 등급 분류 | 설문 응답 기반 A/B/C 등급과 후속 액션 제안 생성 | 마케터 + 백엔드 |

## 6. 입력값 검증 및 참여 정책

리드 데이터 품질을 높이고 현장 확인 시간을 줄이기 위해 설문 제출 단계에서 아래 조건을 필수 검증합니다.

| 항목 | 정책 | 개발 반영 포인트 |
| --- | --- | --- |
| 동의 항목 | 개인정보 수집 동의와 마케팅 활용 동의는 필수 | 두 동의 항목을 분리해 표시하되, 모두 동의해야 설문 제출 가능 |
| 이메일 | 원칙적으로 개인 메일 사용 불가. 회사 메일만 허용 | `gmail.com`, `naver.com`, `daum.net`, `kakao.com` 등 개인 메일 도메인 차단 목록 필요. 프리랜서/학생 선택 시 예외 허용 여부는 추가 논의 |
| 휴대폰 번호 | 숫자만 입력 가능하며, **010 포함 11자리**를 반드시 채워야 함 | 하이픈 자동 제거 또는 숫자 입력만 허용. 정규식 예: `^010\d{8}$` |
| 참여 제한 | 행사 기간 중 전체 1회가 아니라 **하루 1회** 참여 가능 | 중복 기준을 휴대폰 번호 + 행사 일자 또는 리드 ID + 행사 일자로 설정 |
| 경품 재고 | 행사 전체 재고가 아니라 **일자별 재고**로 관리 | 예: 1일차 1등 2개, 2일차 1등 1개처럼 날짜별 수량 설정 |
| 운영자 검색 | 이름 + 휴대폰 뒷자리 4자리로 검색 | 동명이인 또는 뒷자리 중복 시 개인정보 노출을 줄이기 위해 회사명만 추가 선택지로 표시 |
| 지급 처리 | 별도 지급 완료 버튼 없이 **당첨 결과 노출 = 지급 완료**로 처리 | 추첨 실행 시점에 결과 저장과 재고 차감을 함께 처리 |

> **예시:** 행사가 2일간 진행되면 같은 참여자도 1일차 1회, 2일차 1회까지 뽑기에 참여할 수 있습니다. 단, 같은 날짜에는 재참여할 수 없으며 경품 수량도 날짜별로 차감됩니다.

## 7. 서비스 내 AI 활용 방향

서비스 기능 측면에서는 단순 추첨 도구가 아니라 "현장 리드 확보 이후의 마케팅 판단을 돕는 AI 운영 도구"로 포지셔닝합니다.

> **추천 MVP: 리드 품질 점수화**
>
> 관심 제품, 도입 검토 시기, 회사/직무 정보, 상담 희망 여부를 바탕으로 AI가 A/B/C 등급을 부여합니다.
>
> **발표에서 가장 설명하기 쉽고 마케팅 활용 가치가 명확합니다.**

> **확장 후보: 후속 메시지 생성**
>
> 당첨 등수와 설문 응답에 따라 감사 메시지, 상담 안내, 제품 소개 이메일 초안을 자동 생성합니다.
>
> 시간이 남으면 데모에 포함하기 좋은 기능입니다.

## 8. 추첨 로직 제안

| 방식 | 장점 | 주의점 | 추천도 |
| --- | --- | --- | --- |
| 확률 기반 추첨 | 운영자가 등수별 확률을 조정하기 쉽고 이벤트성이 큼 | 특정 등수가 너무 빨리 소진될 수 있음 | 중간 |
| 사전 랜덤 풀 방식 | 등수별 수량 관리가 명확하고 구현 설명이 쉬움 | 예상 참여자 수 또는 전체 풀 크기를 정해야 함 | **높음** |

해커톤 MVP에서는 **사전 랜덤 풀 방식**을 권장합니다. 예를 들어 1일차 예상 참여자 150명, 2일차 예상 참여자 150명처럼 날짜별 풀을 따로 만들고, 각 날짜의 등수별 수량을 무작위 순서로 소진하는 구조입니다.

## 11. API 초안

| 기능 | API | 설명 |
| --- | --- | --- |
| 설문 제출 | `POST /api/leads` | 참여자 정보와 설문 응답 저장. 필수 동의, 회사 메일, 휴대폰 010 포함 11자리 숫자 검증 포함 |
| 참여자 검색 | `GET /api/leads/search?name=&phoneLast4=` | 운영자 화면에서 설문 제출자 조회. 결과가 여러 건이면 회사명으로 선택 |
| 뽑기 실행 | `POST /api/draw` | 행사 일자 기준 참여 여부 확인 후 등수와 경품 결과 반환. 반환 즉시 지급 완료로 간주 |
| 경품 현황 | `GET /api/prizes` | 행사 일자별 등수 초기 수량, 당첨 수량, 잔여 수량 조회 |
| 참여 이력 | `GET /api/draw/history?leadId=&eventDate=` | 특정 참여자가 해당 행사 일자에 이미 참여했는지 확인 |
| AI 분석 | `POST /api/ai/lead-score` | 리드 등급, 사유, 후속 액션 제안 생성 |

## 12. 화요일 개발 논의 체크리스트

1. 해커톤 규칙상 허용되는 AI 코딩 도구와 사용 범위를 확인합니다.
2. Codex, Claude Code 등 어떤 도구를 누가 담당해서 사용할지 정합니다.
3. AI에게 줄 기능 명세, 화면 명세, API 명세를 먼저 정리합니다.
4. 설문 폼을 직접 만들지, 기존 Google Form을 활용할지 결정합니다.
5. 개인정보 수집 동의와 마케팅 활용 동의 문구를 확정합니다.
6. 개인 메일 차단 도메인 목록과 프리랜서/학생 예외 처리 기준을 정합니다.
7. 휴대폰 번호는 숫자만 입력, 010 포함 11자리 조건으로 확정합니다.
8. 저장소를 Google Sheets로 갈지, DB로 갈지 결정합니다.
9. 추첨 로직을 사전 랜덤 풀 방식으로 확정할지 논의합니다.
10. 일자별 등수별 경품 수량과 5등 재고를 유한/무제한 중 무엇으로 볼지 정합니다.
11. 행사 기간이 여러 날일 때 중복 참여 기준을 "휴대폰 번호 + 행사 일자"로 둘지 정합니다.
12. 검색 결과가 여러 건일 때 회사명만 노출해 선택하는 UI가 충분한지 확인합니다.
13. 현장 네트워크 장애 대응과 관리자 기능이 MVP에 필요한지 개발자와 논의합니다.
14. 운영자 로그인 또는 단일 운영 화면으로 충분한지 정합니다.
15. AI 기능은 리드 등급 분류를 MVP로 하고, 후속 메시지는 확장 기능으로 둘지 결정합니다.
16. 해커톤 데모 시나리오를 "AI로 개발한 과정 → QR 설문 → 운영자 검색 → 뽑기 → AI 리드 등급 확인"으로 구성할지 정합니다.

> AI 코딩 도구로 빠르게 구현한 오프라인 부스 이벤트 운영 솔루션입니다. 설문, 리드 확인, 경품 추첨, 결과 저장을 하나로 연결해 대기 시간을 줄이고, 서비스 내 AI로 리드 품질과 후속 액션까지 제안합니다.
